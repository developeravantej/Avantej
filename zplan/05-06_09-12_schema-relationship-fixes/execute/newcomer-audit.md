# Newcomer Migration Audit — Phase 0 follow-up 2

**Scope:** the 8 file-only `.sql` migrations in `packages/db/src/migrations/tenant/`
that were generated by drizzle-kit AFTER the embedded historical baseline was
hand-maintained. They were emitted against a schema state drizzle-kit thought
was empty, so several recreate tables/columns the embedded historical migrations
already created. Without idempotency guards, re-running them on an existing
tenant fails with `relation "X" already exists`.

**Apply order at runtime** (per `scripts/gen-tenant-migrations.ts`):
HISTORICAL_ORDER (the original 34 hashes) is applied first, then the 8
newcomers lex-sorted at the end. So at re-run time the state produced by the
historical migrations is already in place.

**Decision rule per file**

- Every statement is DUPLICATE of an earlier embedded migration → marker no-op
  (`SELECT 1;` plus comment explaining what it superseded). File and hash kept
  so already-stamped tenants don't see a missing hash.
- Every statement is NOVEL → rewrite with idempotent guards
  (`IF NOT EXISTS`, `DO $$ ... EXCEPTION WHEN duplicate_object THEN NULL; END $$;`).
- Mixed → keep only NOVEL statements (with guards) and drop duplicates as
  comments.

## 1. `0004_talented_terrax.sql`

**Original:** 19 `CREATE TABLE` (member_profiles, service_members,
service_category_config, customer_profiles, notification_preferences,
notifications, user_activity_log, package_instances, preferred_times,
class_slots, waitlist_entries, recurrence_rules, announcements, expenses,
payment_items) + 30 `ALTER TABLE ... ADD COLUMN` on services/appointments/
payments + many FK and INDEX statements + `ALTER TABLE hierarchy_nodes DROP

**Classification:** **All DUPLICATE.** Every statement is byte-for-byte
identical to `0005_schema_enhancement.sql`, which is in HISTORICAL_ORDER and
runs earlier. (Confirmed via grep on every `CREATE TABLE` name + comparison
of the trailing ALTERs/INDEXes.)

**Action taken:** rewritten as a marker no-op. The file body is now a
comment listing what it superseded plus `SELECT 1;`.

## 5. `0014_expenses_currency_myr.sql`

**Original:**
1. `UPDATE expenses SET currency = 'myr' WHERE currency = 'usd';`
2. `ALTER TABLE expenses ALTER COLUMN currency SET DEFAULT 'myr';`

**Classification:** **Mixed but naturally idempotent.**
- Statement 1 is a NOVEL data correction. No embedded migration runs this.
  It is naturally idempotent by predicate — once all rows are 'myr', it
  matches nothing.
- Statement 2 is a DUPLICATE: `0016_worried_wolfpack.sql` already does
  `ALTER TABLE expenses ALTER COLUMN currency SET DEFAULT 'myr';`. PostgreSQL
  `ALTER COLUMN ... SET DEFAULT` is idempotent — re-running succeeds silently.

**Action taken:** kept both statements verbatim with an explanatory comment.
No `IF NOT EXISTS`-style guards needed because Postgres already gives both
statements idempotency for free.

## 6. `0014_lively_jane_foster.sql`

**Original:** the entire Phase 1 service-category commission system —
`TRUNCATE commission_splits CASCADE`, `ALTER TABLE services DROP COLUMN
commission_percentage`, six new tables (trainer_tiers,
category_commission_configs, commission_coach_slots, commission_tier_rates,
commission_conditions, commission_condition_rates), all their FKs/indexes,
`members.trainer_tier_id` with FK + index, `appointment_staff.slot_index`,
`appointments.sales_order_id` + FK + index, eight `commission_splits`
column adds + index, plus eight `service_category_config` column drops.

**Classification:** **All DUPLICATE** of `0029_service_category_commission.sql`.
Identical text (we have a hand-edited destructive migration that ships in the
embedded set; the newcomer is a phantom drizzle-kit recreation of the same
content).

**Action taken:** rewritten as a marker no-op.

> **Important non-blocker:** the original newcomer contained
> `TRUNCATE commission_splits CASCADE` and `DROP COLUMN commission_percentage`.
> Marking it as a no-op means those destructive operations are not re-applied
> on tenants past the historical baseline. That is intentional and correct —
> they were already executed via `0029_service_category_commission` and a
> re-truncate would silently destroy live commission data. The marker comment
> documents this so a future reader doesn't think the data wipe was lost.

## 7. `0019_gray_rachel_grey.sql`

**Original:**
1. `ALTER TABLE "package_instances" ADD COLUMN "preferred_trainer_id" uuid;`
2. `ALTER TABLE "package_instances" ADD CONSTRAINT "package_instances_preferred_trainer_id_members_id_fk" FOREIGN KEY ("preferred_trainer_id") REFERENCES "public"."members"("id") ...;`

**Classification:** **All NOVEL.** No embedded migration adds
`package_instances.preferred_trainer_id`. Confirmed against the live tenant
schema (`packages/db/src/schema/tenant/package-instances.ts:64`).

**Action taken:** rewritten with idempotent guards:
- `ADD COLUMN IF NOT EXISTS` for the column.
- `DO $$ BEGIN ... ADD CONSTRAINT ...; EXCEPTION WHEN duplicate_object THEN NULL; END $$;`
  for the FK (PostgreSQL has no `ADD CONSTRAINT IF NOT EXISTS`).

## 8. `0020_add_coach_intake_tables.sql`

**Original:**
1. `CREATE TABLE coach_intake_availability (...)`.
2. `CREATE TABLE coach_intake_exceptions (...)` with a UNIQUE composite constraint.
3. Two `ADD CONSTRAINT ... FOREIGN KEY` statements.
4. Three `CREATE INDEX` statements.

**Classification:** **All NOVEL.** No embedded migration creates these tables.

**Action taken:** rewritten with idempotent guards:
- `CREATE TABLE IF NOT EXISTS` for both tables.
- Two `DO $$ ... EXCEPTION WHEN duplicate_object ...` blocks for the FKs.
- `CREATE INDEX IF NOT EXISTS` for all three indexes.
- Inline `CONSTRAINT "coach_intake_exc_unique" UNIQUE(...)` is part of
  `CREATE TABLE IF NOT EXISTS`, so it's only attempted on first creation —
  inherently idempotent.
