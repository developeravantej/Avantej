## 1. Bundle Analysis — `manualChunks` Strategy

### Finding S1: `recharts` is not a dependency — phantom chunk [CRITICAL]

The plan proposes `"vendor-charts": ["recharts"]` in `manualChunks`, but `recharts` is **not listed in `apps/web/package.json`** (neither dependencies nor devDependencies). Grep confirms zero imports of `recharts` anywhere in `apps/web/src/`.

Rollup will either silently ignore the entry (wasting config) or — depending on version — throw a build error when it cannot resolve the module for the manual chunk.

**Fix:** Remove the `"vendor-charts"` chunk entirely. If charting is added later, add the chunk at that time.

### Finding S2: `radix-ui` wrapper AND individual `@radix-ui/*` packages are both installed [MEDIUM]

`package.json` lists both `"radix-ui": "^1.4.2"` (the umbrella wrapper) and 9 individual `@radix-ui/react-*` packages. The plan's `"vendor-radix"` chunk lists only individual packages (`@radix-ui/react-dialog`, etc.), but 5 files import from `"radix-ui"` (the wrapper). The wrapper re-exports everything, so it will pull the full Radix bundle into whatever chunk contains it — potentially the main chunk, defeating the purpose of the `vendor-radix` split.

**Fix:** Phase 6 (Task 6.2) must execute **before** Phase 5 (Task 5.1), or at minimum the `manualChunks` config must also include `"radix-ui"` in the `vendor-radix` array until the wrapper imports are eliminated. Current phase ordering (6 after 5) means Phase 5 ships with a broken radix chunk strategy.

### Finding S3: Missing large dependencies from `manualChunks` [MEDIUM]

Dependencies omitted from `manualChunks` that are large and widely used:

| Dependency | Import count | Approx size | Recommendation |
|---|---|---|---|
| `lucide-react` | 170 files | ~150KB+ (icon set) | Add to `vendor-ui` chunk |
| `sonner` | 71 files | ~30KB | Include with vendor-ui or leave in main |
| `react-hook-form` + `@hookform/resolvers` | 21 files | ~50KB | Add to `vendor-forms` chunk |
| `zod` | widespread | ~60KB | Add to `vendor-forms` or `vendor-core` |
| `better-auth` | auth layer | ~40KB | Could go in `vendor-auth` |

Without explicit assignment, these all land in the main chunk, undermining the <1.5MB target.

### Finding S4: No circular chunk dependency risk [INFO]

The proposed chunks (`vendor-react`, `vendor-tanstack`, `vendor-radix`) are cleanly separated — React is a peer dep of TanStack and Radix but Rollup handles peer deps correctly across manual chunks. No circular dependency risk from the proposed grouping.

## 2. Lazy Loading — `createLazyFileRoute` API

### Finding S5: No existing lazy route patterns in codebase — unvalidated API [HIGH]

Grep for `createLazyFileRoute`, `createLazyRoute`, and `.lazy.` across `apps/web/src/routes/` returns **zero matches**. The project has never used TanStack Router's lazy loading. All routes use `createFileRoute` with eagerly-loaded components.

The `routeTree.gen.ts` file (auto-generated by `@tanstack/router-plugin/vite`) shows no lazy imports. This means:

1. The TanStack Router Vite plugin's code generation must be verified to support the `.lazy.tsx` file convention. At `@tanstack/react-router` v1.114.x, the `createLazyFileRoute` API exists and the file-based router plugin **does** support `{name}.lazy.tsx` files automatically — but this has never been tested in this codebase.

2. The plan says to use `createLazyFileRoute` for 5 routes. This is the correct API for TanStack Router v1.x file-based routing. However, the split must follow the convention precisely: the **non-lazy file** keeps `createFileRoute` with `beforeLoad`/`loader`/`validateSearch`, and the **`.lazy.tsx` file** uses `createLazyFileRoute` exporting only the `component`. Getting this wrong will break route guards (RBAC `beforeLoad` checks) or duplicate component definitions.

**Risk:** Since there are zero existing examples in the codebase, the implementer has no local reference. The plan should include a proof-of-concept on ONE route first (e.g., `purchase-orders/view.tsx`) with verification that:
- `routeTree.gen.ts` regenerates correctly with lazy imports
- `beforeLoad` guards still execute before chunk fetch
- Dev server hot-reload works with the split files

### Finding S6: Cloudflare plugin may interfere with lazy chunk loading [HIGH]

The `@cloudflare/vite-plugin` (`cloudflare()`) is loaded unconditionally in `vite.config.ts` (line 9). This plugin transforms the build for Cloudflare Workers/Pages deployment. In production builds, it may:

1. Bundle all JS into a Worker-compatible format that defeats route-level code splitting
2. Alter the asset manifest so lazy chunks cannot be resolved at runtime

The plan (Task 5.4) proposes gating it behind `process.env.CF_DEPLOY === "true"`. This is correct but **must be done BEFORE Task 5.1/5.2**, not after. If `manualChunks` and lazy routes are configured while `cloudflare()` is still active, the build output will be Cloudflare-transformed and the chunk strategy may not work as expected during validation.

**Fix:** Reorder Task 5.4 to be the FIRST task in Phase 5, not the last.

## 3. Query Cache Invalidation vs. Proxy Mock

### Finding S7: `orpc.*.key()` pattern will silently break with Proxy mock [HIGH]

Production code uses `orpc.roles.list.key()`, `orpc.members.list.key()`, `orpc.products.list.key()`, etc. to construct query keys for `invalidateQueries`. This pattern calls `.key()` on the oRPC client's query helper — it returns a structured array like `["roles", "list"]`.

The Proxy-based mock returns `makeMockNamespace()` for every property access, which means `mockClient.roles.list.key()` would return... another Proxy, not an array. This breaks any test that:
1. Calls `invalidateQueries({ queryKey: orpc.X.Y.key() })` and checks the invalidation happened
2. Asserts on query key values

Looking at the test files, `useApiMutation.test.tsx` already mocks `invalidateQueries` separately, so it may not hit this. But `useRoles.ts`, `useUserAssignment.ts`, and multiple form hooks use `orpc.*.key()` directly. If any test exercises these code paths, the Proxy mock will silently produce wrong query keys.

**Fix:** The Proxy mock's `get` handler must also handle a `.key` property access, returning a function that produces a deterministic array (e.g., `() => ["mock", parentPath]`). This is not in the plan's mock implementation.

### Finding S8: Global `invalidateQueries()` call in error handler [LOW]

`apps/web/src/utils/orpc.ts:14` calls `queryClient.invalidateQueries()` with **no arguments** (invalidates ALL queries) in the global error toast retry handler. This is a performance concern — a single API error retries the entire cache. Not introduced by this plan, but worth noting since Phase 5's lazy loading will increase the number of cached route-level queries that get unnecessarily refetched.

## 4. Module Loading — Import Graph After Phase 4 Splits

### Finding S9: No `optimizeDeps` config — Vite defaults are fine [INFO]

`vite.config.ts` has no `optimizeDeps` configuration. Vite's default pre-bundling handles dependency optimization automatically. The Phase 4 feature-folder extraction creates new internal imports (not new npm deps), so `optimizeDeps` does not need updating.

### Finding S10: Feature module double-loading risk is low [INFO]

Phase 4 extracts god-files into `features/<name>/` modules imported by thin route shells. Since these are standard ES module imports (not dynamic `import()`), Vite/Rollup will deduplicate them in the bundle. A module imported by both a route file and another feature file will only appear once in the output. No double-loading risk.

However, if Phase 5's lazy routes are combined with Phase 4's feature extraction, a shared feature module (e.g., a common hook used by both a lazy and non-lazy route) could end up duplicated across chunks. Rollup's `manualChunks` does not handle internal modules — only the listed npm packages. Shared internal modules between lazy chunks should be monitored in the build output.

## 5. Code Splitting Effectiveness — Dependency Tree

### Finding S11: `lodash-es` confirmed unused — safe to remove [INFO]

Zero imports of `lodash-es` or `lodash` in `apps/web/src/`. Plan correctly identifies this for removal.

### Finding S12: `tw-animate-css` is used — do NOT remove [MEDIUM]

`apps/web/src/index.css` line 2: `@import "tw-animate-css"`. The plan (Task 6.1) says to "grep usage in CSS and JS; if zero, remove." A JS-only grep would miss this CSS import. The package provides Tailwind animation utilities and IS in use. Removing it would break animations site-wide.

**Fix:** Mark `tw-animate-css` as confirmed-in-use in the plan. The `depcheck` tool may also flag it as unused since it only appears in CSS, not JS imports.

### Finding S13: `@tanstack/react-form` has very low usage — candidate for removal [LOW]

Only 3 files import `@tanstack/react-form` (login, sign-in, sign-up forms). The project primarily uses `react-hook-form` (21 files). Having two form libraries adds ~40KB to the bundle. Not in the plan's scope but worth flagging for Phase 6.

### Finding S14: `next-themes` is a minor dep concern [LOW]

Only 2 files use `next-themes` (theme provider + sonner component). The package is designed for Next.js and includes Next.js-specific code that won't tree-shake in a Vite build. Consider replacing with a lighter theme toggle (~2KB savings). Not blocking.

## 6. Cloudflare Plugin Details

### Finding S15: `@cloudflare/vite-plugin` transforms the entire build [HIGH]

`vite.config.ts` line 1: `import { cloudflare } from '@cloudflare/vite-plugin'` — loaded unconditionally on line 9.

This plugin (`@cloudflare/vite-plugin` v1.13.x) does the following:
- In **dev mode**: Runs a Cloudflare Workers-compatible dev environment (miniflare)
- In **build mode**: Transforms output for Cloudflare Pages/Workers deployment, potentially altering the asset manifest and chunk structure

For a web frontend app that deploys to Cloudflare Pages as static assets, the plugin may be unnecessary or even counterproductive — Cloudflare Pages serves static files directly. The plugin is more relevant for Workers (server-side) or Pages Functions.

The plan's fix (Task 5.4: gate behind env var) is correct in principle. However, `process.env.CF_DEPLOY` is a Node.js env var, not a Vite env var. In `vite.config.ts`, it should be accessed via `process.env` (which works in the config file context) but the plan should verify that the Cloudflare deploy CI step sets this env var.

**Fix:** Use `process.env.CF_DEPLOY` in `defineConfig` (works in config context). Alternatively, use Vite's `mode` parameter: `vite build --mode cloudflare` and check `mode === "cloudflare"` in the config function.
