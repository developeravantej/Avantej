## Change 2: Invitation Scope Fix (Ticket B)

### Files touched

| File | Change |
|------|--------|
| `packages/api/src/routers/invitations.ts` | `list` procedure: conditional filter on `invitedBy` |
| (No frontend change) | — |

### Callers / importers

Grep: `client.invitations.list` usages:

- `apps/web/src/routes/_authenticated/dashboard/_layout/access-control/invitations.tsx` (documented Section 14d)
- Potentially: `components/invitations/invitations-page.tsx` (referenced by the route file)

**Verify before implementation:** run `grep -r "invitations.list" apps/ packages/` to confirm no other caller.

### Breakage surface

| Before | After |
|--------|-------|
| Admin A calling `list` → only Admin A's invitations | Admin A calling `list` → all org invitations (if they have `user_management:read`) |
| Staff C calling `list` → only their own invitations (empty for most) | Staff C calling `list` → only their own (if no permission) |

Return shape unchanged. No existing caller breaks. Just more rows returned for privileged callers.

### Deployment coupling

- Backend-only. No frontend deploy required.
- Safe to deploy alone.
- Indirect UX improvement: the Invitations page immediately shows more rows for admins after the backend deploys. No flag needed.

### Rollback

Revert the router file diff. No data changes, no migration.

### Nullable / Optional Concerns

- `invitations.invitedBy` is non-nullable (each invitation has an inviter)
- The permission check calls `requirePermission` which throws on failure — wrap in try/catch per the plan to degrade gracefully to "own only"

### Test Coverage

Required before merge:
- Integration test: admin with permission sees all
- Integration test: user without permission sees only own
- Integration test: no invitations → empty array (not error)

**Modified files:**

- `apps/web/src/components/app-sidebar.tsx` — added Rooms entry (line 136) + `DoorOpen` import
- `apps/web/src/components/calendar/add-appointment-modal.tsx` — inline "Create one →" empty state + contextual `employeePlaceholder` + disabled Employee select

- `apps/web/src/routeTree.gen.ts` — regenerated by TanStack Router
- `zhub/index.md`, `zhub/pages/web-dashboard-appointment-view.md` — hub docs updated

### Callers of `rooms` router

Existing callers (verify before shipping):

- `apps/web/src/components/calendar/add-appointment-modal.tsx` — calls `client.rooms.list` for the dropdown

After this change, the same `list` endpoint is called from two places. Both use the same filters. No behavior change for the appointment modal.

### Schema considerations (as shipped)

`rooms` tenant table: `id`, `name`, `type` (NOT NULL), `capacity` (NOT NULL integer), `branchId` (NOT NULL, FK → `hierarchyNodes.id` `ON DELETE RESTRICT`), `isActive` (NOT NULL default true), `createdAt`, `updatedAt`. No `notes` column; no separate `organizationId` column (tenant-DB-scoped).

### Nullable concerns (as shipped)

- `rooms.branchId` non-null — form validates via required combobox
- `rooms.capacity` non-null — form treats as required integer
- Deletion: UI exposes Deactivate / Reactivate (both via `rooms.update({ isActive })`); no hard-delete UI surface. `rooms.delete` router procedure internally soft-deletes to respect the `ON DELETE RESTRICT` on `branchId`.

### Deployment coupling

- Frontend + seed-script only. No migration. Safe to deploy alone.
- Backend router already shipped (no changes needed).

### Rollback

Remove the new route file + sidebar entry. Revert the appointment-modal and seed-script diffs. Regenerate `routeTree.gen.ts`. No data affected.

## Change 3b: Dynamic Installment Plans — SHIPPED 2026-04-17 (out-of-plan)

**Status: SHIPPED on branch `Customer-app`. See `zdone/17-04_dynamic-installment-plans.md`.**

This work was not scoped in the original dashboard-completeness plan but landed in the same window and interacts with the shipped dashboard. Called out here so doc patches #4 and #12b-#14 absorb it.

### Files touched

**Schema / backend:**

- NEW tenant table `installment_plans` via migration `0017_installment_plans` (embedded in `migrate-tenant.ts`)
- `packages/services/src/installment-plan.service.ts` (new)
- `packages/api/src/routers/installment-plans.ts` (new, registered in `baseRouter`)
- `packages/services/src/installment.service.ts` — `createInstallmentSchedule` now takes `installmentsTotal: number`; `getAdminInstallmentOverview` gained `search / dueBefore / dueAfter / paymentPlanCode` filter params
- `packages/api/src/routers/package-instances.ts` — plan resolved by code at handler
- `packages/api/src/routers/services.ts` — `availablePaymentPlans` widened from `z.enum([...])` to `z.array(z.string())` with existence validation
- `packages/api/src/routers/installments.ts` — `adminOverview` accepts the 4 new filter inputs

**Frontend:**

- NEW `apps/web/src/routes/_authenticated/dashboard/_layout/settings/installment-plans.tsx`
- `apps/web/src/components/app-sidebar.tsx` — added Installment Plans entry under Config
- `apps/web/src/components/forms/service-form.tsx` — dynamic checkboxes sourced from `client.installmentPlans.list`
- `apps/web/src/components/tables/service/view/data-table.tsx` — cast widened to `string[]`
- `apps/web/src/routes/_authenticated/dashboard/_layout/packages/installments/view.tsx` — filter row + typed `plansMap`

### Breakage surface

| Before | After |
|--------|-------|
| `services.availablePaymentPlans: z.enum(["full","half","quarterly"])` | `z.array(z.string())` validated against `installment_plans.code` | 
| Hardcoded `planToTotal` map in scheduler | Plan resolution via `installmentPlans` table at the handler layer |

Backward-compatible because seed rows (`full`, `half`, `quarterly`) exactly match legacy literals — all historical `package_instances.paymentPlanType` rows remain valid.

### Native-app note

Phase 5 (native app integration) was SKIPPED per user instruction. Native continues to read legacy codes — safe because the seed preserves them.
