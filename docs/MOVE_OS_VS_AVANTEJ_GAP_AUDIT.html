MOVE OS  vs  Avantej — Tenant Dashboard Gap Audit

Live crawl of move-session-billing-staging.onrender.com (competitor tenant OS) vs the Avantej tenant dashboard codebase. 18 domains audited by parallel repo agents. MOVE OS is a single-region-per-tenant, multi-currency gym-billing OS; use it as a feature reference, not an architecture model.

Verdict

Avantej is in a strong position: on the four highest-frequency daily-use modules — Dashboard/KPIs, Clients, Commission ledger, and Users/RBAC — it is already at or beyond MOVE OS parity. Its dashboard is broader (staff leaderboard, churn/LTV/class-fill, hierarchy-aware scope selector), its Customer-360, appointments engine (recurrence, credit debit, 24h locks, status history), and its versioned 'drive-engine' commission settings are genuinely richer than the MOVE spec. Of 17 audited domains, 4 are present, 10 are partial, and only 3 are truly absent. The headline is that Avantej is not missing whole product areas so much as missing specific, high-leverage sub-features inside areas it already has — plus three genuinely absent operational modules.

The biggest gaps cluster around money correctness, back-office operations, and onboarding, and these are the P0s. First, single-currency assumptions are hardcoded across the commission ledger, branch display, and package pricing — a multi-country tenant (MOVE is seeded MY/TH/SG) would see co-mingled, incorrect totals, which is a correctness bug, not just a cosmetic one. Second, the Reports area is only an aggregate KPI dashboard: none of MOVE's 10 row-level operational reports (Sales, Collections, AR-aging, Coach productivity, Refunds, Redemptions, Services-owed) are surfaced even though the underlying data exists — this is the single largest surface-area gap. Third, branches lack a per-branch company/tax profile, per-branch tax rates, and per-branch invoice/receipt numbering, which are compliance-relevant for multi-outlet operators. Fourth, payroll locking is per-split/per-batch rather than a month-keyed Open/Locked period with auto-lock and enforced immutability, so back-dated edits can silently land in a settled month. And fifth, there is no self-service CSV import — the only importer is a developer-run xlsx CLI, which blocks scalable tenant onboarding.

The three absent modules — Import (CSV), Data Health, and Danger Zone — are the clearest 'missing modules,' but they are not equal in urgency. Import is P0 because it gates every new tenant's onboarding and is the difference between a developer-assisted and a self-serve business. Data Health is P1: valuable for trust and catching money leaks, and Avantej already has the DriftTab UI pattern to copy. Danger Zone is P2 — expected polish for sandbox/demo tenants but not on the money-flow critical path. Encouragingly, nearly every gap has existing scaffolding to build on (the ETL loaders for import, the Stripe reconciler UI for data health, the CSV codec and generic table-dump for exports, commission_cycle_configs for payroll windows), so the work is largely surfacing and generalizing capabilities that already exist rather than green-field building. The recommended sequence is: close the multi-currency correctness gap and ship the reports suite first, then per-branch tax/numbering and payroll locking, then self-service import — after which Avantej would meet or exceed MOVE OS across every core money and operations surface.

Absent modules — the true "missing" (3)

Whole capability areas MOVE OS has that Avantej does not. These are the clearest "mimic" targets.

Import (CSV) Absent

MOVE has: A tenant-admin self-service CSV importer in the dashboard: entity picker (Clients, Users, Branches, Service categories, Package templates, Payees, Packages, Payments, Brought-forward balances), downloadable per-entity templates, per-row validation with a preview-before-commit table, and re-runnable idempotent jobs.

Why it matters: This is the onboarding gate. Every new gym tenant arrives with historical data (members, packages, opening balances) in spreadsheets. Without UI import, onboarding requires a developer to hand-run the xlsx CLI ETL per client — it does not scale, blocks self-serve signups, and today Sales/Payments/Packages/redemptions are marked BLOCKED in that ETL anyway.

Build sketch

Add route settings/import/view.tsx with an entity picker + dropzone; add papaparse client-side; new oRPC router packages/api/src/routers/data-import/ (validate.procedures.ts = importPreview with per-row Zod errors, commit.procedures.ts = transactional importCommit) reusing the existing canonical DTOs/loaders (apps/server/scripts/migration/core/canonical.ts + core/loaders/*) and porting core/crosswalk.ts idempotency; header-only CSV template endpoint per entity; add an import_jobs tenant table for history; unblock Payments/Packages/Payees/Service-categories/opening-balance loaders. Guard with requirePermissionOrpc + assertOrgContextMatch.

Data Health (integrity checks) Absent

MOVE has: A tenant-facing 'Data Health' page running a battery of ~24 pass/fail integrity checks over business data (non-negative credit balances, credits <= package size, installment credits sum = package size, unlocked credits reconcile to money collected, commission <= sale, commission-vs-ledger, every sale has allocation rows, orphaned references, unique sign-in emails) with an 'N of 24 need attention' summary and expandable failing-row samples.

Why it matters: Gym billing tenants accrue silent data corruption (over-consumed credits, commission exceeding sale value, orphaned records) that leaks money and erodes trust. MOVE lets an owner self-diagnose; Avantej has no runtime business-data integrity checks at all — only a platform-admin Stripe reconciler that tenants can't see.

Build sketch

Add packages/services/src/data-health.service.ts runIntegrityChecks(tenantDb, orgId) returning typed {id,label,category,status,failingCount,sampleRows[]}; router packages/api/src/routers/data-health.ts (run + summary) guarded by requirePermissionOrpc('reports:read'); implement each check as a discrete Drizzle/SQL assertion; UI route data-health.tsx reusing the SeverityBadge/EmptyState pattern from platform-admin-payments/DriftTab.tsx; optional nightly cron writing data_health_snapshots for instant load + trending, and a dashboard alert when failingCount>0.

Danger Zone Absent

MOVE has: A tenant-facing Danger Zone settings section: a Sandbox Reset that wipes packages + bookings while preserving branches/users/clients/coaches/categories/payees/promos/templates (gated by a typed 'CLEAR ALL PACKAGES' confirmation phrase), plus a per-record-type permanent hard-delete tool (Client/Package/Session/User/Branch/Service category/Package template) with search-then-select UX and a dedicated hard-delete audit log.

Why it matters: Demo/sandbox tenants and mis-imports need a clean reset without a developer; MOVE gives operators a safe, audited self-serve purge. Avantej's only hard-delete is platform super-admin whole-tenant deletion — a tenant admin cannot selectively clear test data or purge a record type from within their own dashboard. Lower urgency than money-flow gaps but expected in a mature product.

Build sketch

Add router packages/api/src/routers/danger-zone/ (resetSandbox, hardDelete) admin-only + requirePermissionOrpc('danger_zone:manage'); packages/services/src/danger-zone.service.ts doing a transactional delete of package_instances + appointments while preserving the protected tables and validating the typed confirmation phrase server-side; hardDelete(recordType, ids[]) respecting FK/cascade order; a tenant hard_delete_audit table via idempotent migration + gen:migrations; UI settings/danger-zone.tsx with a typed-phrase modal + record-type search/multi-select red-confirm panel; add the 'danger_zone:manage' permission to seed-rbac.ts.
