Commission Calculator — Refactor Design

Restructuring commission-calculator.service.ts from one 400-line side-effecting function into a three-phase pipeline: gather → plan (pure) → persist. The arithmetic in commission-math.ts stays untouched — this targets only the orchestration that's hard to reason about. Behavior is identical; it's a pure structural change.

② Proposed — three-phase pipeline

I/O — reads only Pure — no DB, no audit, fully testable I/O — writes only
1

loadCommissionContext READS

(db, serviceId) → CommissionContext | null
All reads happen here, once, shared by both entry points.
  • service → categoryId → active categoryCommissionConfig
  • all commissionCoachSlots for the config
  • rate table — tier rates, or every condition + its condition-rates
  • latest configVersionId (for the cap aggregate join)
returns CommissionContext — a typed, immutable snapshot. No decisions made yet.
2

planSplits PURE

(context, input) → { splits: PlannedSplit[]; skipped: SkipReason[] }
The whole decision, as one pure function. No DB, no audit, no console. This is the part that was hard to reason about — now unit-testable in isolation.
  • dedupe assignments by slotIndex (fix #3)
  • match the condition by a single numeric value — attendeeCount or quantity
  • filter eligibility once → emit SkipReason instead of logging
  • redistribute unclaimed weightage (calls existing commission-math)
  • resolve rate → baseAmount → finalAmount (multiply-then-floor, fix #1)
  • compute splitPercentage
returns PlannedSplit[] (what to write) + SkipReason[] (why each staff was dropped) — caps NOT yet applied.
3

persistSplits WRITES

(db, plan, { actor, earnedAt }) → CommissionSplit[]
The only impure phase. Every write lives here, applied uniformly.
  • apply per-cycle cap (applyCommissionCaps) to each planned split
  • insert into commission_splits — with the 23505 race-skip handling
  • writeAudit per created split + one batched audit for all skips
returns the inserted CommissionSplit[] — same shape callers get today.
The two entry points collapse to ~15 lines each — they only differ in how they feed phase 2:
calculateCommissionForAppointment()
  • ctx = loadCommissionContext(db, serviceId)
  • plan = planSplits(ctx, { matchValue: attendeeCount, mode: "operator", quantity: 1, requireTrainerRole: true })
  • return persistSplits(db, plan, { actor, earnReason })
calculateCommissionForPos()
  • ctx = loadCommissionContext(db, serviceId)
  • plan = planSplits(ctx, { matchValue: quantity, mode: "threshold", quantity: N, requireTrainerRole: false })
  • return persistSplits(db, plan, { actor, earnReason })

③ The new types

// commission-calculator.types.ts — the contracts between phases

interface CommissionContext {        // phase 1 output — immutable snapshot
  config: CategoryCommissionConfig;
  slots: SlotConfig[];           // all coach slots (filled + absent)
  rates: RateTable;               // tier rates OR conditions+condition-rates
  configVersionId: string | undefined;
}

interface PlanInput {
  assignments: StaffAssignment[];
  members: Map<string, MemberSnapshot>;  // pre-fetched by loader
  unitPriceCents: number;
  quantity: number;
  matchValue: number;             // attendeeCount | quantity
  mode: "operator" | "threshold"; // unifies the two matchers
  requireTrainerRole: boolean;
}

interface PlannedSplit {           // phase 2 output — ready to insert, pre-cap
  staffId: string;
  slotIndex: number;
  trainerTierId: string;
  effectiveWeightageBp: number;
  baseAmountCents: number;
  finalAmountCents: number;     // pre-cap; persist applies the cap
  splitPercentage: number;
  conditionId: string | null;
}

interface SkipReason {              // replaces scattered console.warn calls
  staffId: string;
  reason: "no_coach_slot" | "member_not_found" | "role_mismatch"
        | "no_tier" | "no_tier_rate" | "no_condition_rate";
}

④ What it buys you

✓
Decision is testable without a DB
planSplits is pure — feed a context, assert the splits + skips. No mocks, no transactions.
✓
One validation path
Eligibility checked once in the planner. The in-loop "safety net" re-check disappears.
✓
Duplication gone
~220 lines of near-identical entry-point code collapses to two thin wrappers over one pipeline.
✓
Skip-reasons centralized
SkipReason[] replaces 8+ scattered log sites; persist logs/audits them uniformly in one place.
✓
Reads batched up front
All queries in phase 1; the per-staff loop no longer does N+1 member re-lookups.
✓
Side effects at the edge
Every write lives in persistSplits — easy to wrap in one transaction, easy to audit.

⑤ What must NOT change

🔒
Behavior-preserving guarantee
The math module is reused as-is. These invariants are carried over verbatim and asserted by a diff-test on real splits:
  • Fix #1 — multiply amount × weightage × quantity, then floor once
  • Fix #2 — coach-slot weightages must sum to exactly 10000bp
  • Fix #3 — dedupe assignments by slotIndex before any math
  • Per-cycle cap logic + configVersionId anchoring (F-COM-B)
  • 23505 concurrent-cancel race handling on insert
  • comp-order / commission-excluded guard
⚠ One semantic call needs sign-off: merging the appointment operator matcher and POS threshold matcher behind a single mode flag.
