Avantej · Commission System · Architecture Brainstorm

From "trainer splits" to a scalable commission model

Today's engine is delivery-shaped and trainer-locked. This doc reframes commission as stackable tracks so marketing, sales, and future teams earn cleanly — and shows the schema + UI/UX + build order. Decisions below were optimized for how you scale, not lowest upfront effort.

Model
Option B — Tracks
Each new team = one track row, not an engine rewrite. 90% of a rule-engine's flexibility at a third of the complexity.
Stacking
Separate pots, per-track policy
Delivery & origination are different money. Encoded as a column, so a tenant can pick shared-pot without forking code.
Sales basis
Configurable enum · default Net
gross / net / flat as a column. Net by default so you never pay commission on discounted-away money.

①  The reframe: two flavors of commission, not one

Earned bywho performed it — trainers / coacheswho caused the sale — sales rep, marketer, referrer
Triggered onappointment completion / no-show / cancellationthe sale itself (order paid)
Base amountthe session / delivery totalgross · net · or flat spiff on the order
Who splitsall present coaches, by weightage pool (10000bp)usually one closer; optionally a small team
Stacks?—Yes — on top of delivery, same order
In schema today✅ commission_coach_slots + trainer_tiers⚠️ only the requireTrainerRole:false POS hack

Example: Sales Rep A sells a PT package, Trainer B (Senior) delivers it. B earns from the Delivery track; A earns from the Sales track — independently, on the same order. They never compete for one pot.

②  Three models, scored on scaling

A · Rename trainer→earner

Any role earns from the single existing pool.
Scales poorlycheap
  • Reuses all current math
  • One 10000bp pool — sales & trainers fight for the same money
  • No stacking; breaks at the first multi-team payout
✕ Rejected — papers over the real ceiling
CHOSEN

B · Commission tracks

Delivery / Sales / Marketing as stacked tracks per category.
Scales cleanlymoderate
  • Existing trainer logic = the "delivery track", ~unchanged
  • New team = new track row + its tier table
  • Absorbs the POS hack as a real origination track
  • Can evolve into C later if ever needed
✓ Best fit for an SME product that's growing teams

C · Generic rule engine

conditions → basis → beneficiary → rate, fully configurable.
Scales infinitelyheavy
  • Any rule a tenant could imagine
  • Config UI + testing burden is large
  • No tenant has asked for arbitrary rules yet
~ Deferred — premature today, reachable from B

Shared persist + review — caps, insert, audit, approval inbox (one engine)

Each track is a pure planner producing splits; they all feed the same persist & review layer. This is exactly the gather → plan → persist refactor — tracks are just multiple planners, so that refactor is the foundation, not throwaway work.

④  Schema — what changes

// NEW — a category has many tracks (was: one implicit trainer config)
table commission_tracks {
  id            uuid pk
  categoryId    uuid → service_categories
  roleType      text   // "trainer" | "sales" | "marketing" | "referrer" …extensible
  trigger       text   // "on_completion" | "on_sale"
  basis         text   // "delivery_total" | "gross_order" | "net_order" | "flat"  ← the dimension
  paymentType   text   // "fixed" | "variable"  (reused from today)
  poolPolicy    text   // "separate" (default) | "shared"  ← stacking, per-track
  maxBeneficiaries int  // 1 for sales, N for coach pools
  isActive      bool
}
// Trainer config today maps 1:1 onto a roleType:"trainer" track — zero data loss.

// GENERALIZE — tiers gain a roleType so they're role-scoped, not trainer-only
table earner_tiers {         // was: trainer_tiers (renamed + 1 column)
  id uuid pk · name · rank · isActive
  roleType  text          // NEW — "trainer" | "sales" | …  Trainer/Sales tiers coexist
}

// RATES hang off a track, keyed by tier (was: configId + trainerTierId)
table commission_track_rates {
  trackId  uuid → commission_tracks
  tierId   uuid → earner_tiers
  amount   int   // cents if fixed, basis-points if variable
}

// coach slots stay — they belong to delivery-type tracks only
table commission_coach_slots {  trackId  // repointed from configId → trackId · slotIndex · weightageBasisPoints }

// OUTPUT — splits gain provenance so review/payout can group by track
table commission_splits {
  …all existing snapshot fields…
  trackId   uuid     // NEW — which track produced this
  roleType  text     // NEW — denormalized for fast review grouping
  tierId    uuid     // was trainerTierId (rename; still a snapshot, no FK)
}

Migration is additive + a rename: existing trainer config becomes a roleType:"trainer" track, trainer_tiers→earner_tiers with roleType:"trainer" backfilled. No historical split is recomputed.

⑥  Build order — refactor first, tracks are additive

1

Structural refactor (behavior-preserving)

Land gather → plan → persist on the current trainer-only logic. No schema change, no behavior change — proven by an output-diff test on real splits.

✓ zero behavior change
2

Generalize to tracks (additive)

Migrate trainer config → a trainer track, rename tiers, add the tracks/rates tables. The delivery planner is what you already refactored; add a sales planner + the config tabs.

+ new tracks, shared persist

⑦  Why this scales

today
Trainers + tiers. Exactly what ships now — becomes the delivery track, untouched behavior.
+ sales team
Enable a Sales track on a category. One row in commission_tracks + a sales tier table. No engine change.
+ marketing
Enable a Marketing track with a flat spiff basis. Same pattern. Reviews auto-group it.
+ referral program
Add roleType:"referrer". Zero new tables — it's a value in an existing enum + a planner strategy.
if ever needed
Tenant wants arbitrary rules → evolve track → rule-engine (Option C) on the same persist/review foundation.
